# Job Pipeline: Instructions for Claude

This repo is one job seeker's personal pipeline. It scores fit between their
master CV and each job description (JD), checks the CV the way a recruiter and
a hiring manager would read it, tailors the CV without inventing claims, and
tracks outcomes so the user can learn whether their scores predict anything.

Treat this file as the source of truth for how the pipeline behaves. Prefer
consistency over cleverness: scores are only useful if they are comparable
across applications.

---

## Ground rules (every command, every step)

1. **The master CV is ground truth, and the user writes it.** Every score,
   check, tailored CV, and cover letter compares against `cv/master.md`. The
   user is strongly encouraged to draft it themselves; `/cv-master` helps with
   format, evidence interviews, and review, but does not write bullets unless
   the user insists. Any line Claude drafts ends with `<!-- claude-drafted -->`
   until the user rewrites or explicitly approves it. Never edit `cv/master.md`
   outside `/cv-master`, and never with content the user hasn't confirmed.
2. **Never invent claims.** Tailoring rewords, reorders, and re-emphasizes
   facts already in the master CV. A new fact enters the pipeline only by the
   user adding it to `cv/master.md`.
3. **Setup gate.** Before any pipeline command, run
   `python3 scripts/check_setup.py --for <command>`. If it fails, tell the user
   which setup step is missing and offer to run it (`/cv-master` or
   `/setup <step>`). Never fill a missing profile, rubric, or voice by guessing.
4. **Personal context lives in `profile/`.** Read the file a step needs rather
   than assuming:

   | File | Holds | Written by |
   |------|-------|-----------|
   | `cv/master.md` | Master CV, the ground truth | Step 0, `/cv-master` (user-drafted) |
   | `profile/profile.md` | Targets, throughline, domains, proof points, credential to surface, claim rules | Step 1 |
   | `profile/rubric.md` | Weights, domain tiers, level band, hard gaps, pivot threshold, anchor | Steps 2 and 6 |
   | `profile/voice.md` | Writing voice rules, letter header | Step 3 |
   | `profile/export.md` | DOCX export command and format choices | Step 4 |
   | `profile/tracking.md` | Repo privacy, source vocabulary, dashboard choice | Step 5 |

5. **No external sends.** Never submit an application, send an email or
   message, or post anything. Draft it and hand it to the user.
6. **Working vs. frozen.** `cv/`, `jds/`, `analyses/`, `cover-letters/` are
   working folders, revised in place with dated revisions.
   `applications/<company-slug>/<role-slug>/` is a frozen record of what was
   submitted, written once by `/release` and never edited after.
7. **CSV safety.** Read and write `applications.csv` with a real CSV parser.
   Build the full output in memory and verify every row has the same field
   count as the header before writing; a failed write mid-file truncates it.
8. **Writing.** Follow `profile/voice.md` for any generated prose. Describe
   the user and their fit, never the company back to itself.

```
│   ├── master-<track>.md  # optional pivot-track masters (see /tailor)
│   └── <slug>.md          # tailored CVs
├── profile/               # personal context from /setup (steps 1-6)
├── jds/<slug>.md          # one file per job description
├── analyses/<slug>.md     # one scoring report per job
├── cover-letters/<slug>.md
├── applications/<company-slug>/<role-slug>/   # frozen case files (/release)
├── applications.csv       # source of truth for what was scored and applied to
├── outcomes.md            # append-only outcome log
├── calibration/           # /calibrate reports
├── brainstorms/           # grill-me capture files from setup and interviews
├── dashboard/index.html   # generated by scripts/build_dashboard.py
├── templates/             # analysis, cover letter, JD, master CV skeleton
├── scripts/               # deterministic helpers, no LLM calls
└── docs/                  # human documentation
```

**File naming:** one lowercase slug `<company>-<role-slug>` used across `jds/`,
`analyses/`, `cover-letters/`, `cv/<slug>.md`, and the `slug` column of
`applications.csv`. Example: `acme-robotics-director-test-engineering`. The
`<company-slug>` for `applications/` is the company name, lowercased and
hyphenated.

**`applications.csv` columns (12):**
`slug,company,role,date_applied,source,url,jd_status,fit_score,fit_type,outcome,outcome_date,reached_screen`

- `source`: from the vocabulary in `profile/tracking.md` (default `direct`,
  `referral`, `recruiter`, `agency`, `network`).
- `jd_status`: `live_url`, `cached`, `pasted`, or `jd_missing`.
- `reached_screen`: `yes` once any outcome reached `recruiter_screen` or
  further, even if it later ended in rejection; otherwise blank.

## Scoring rubric

The score is a **0-100 fit score** from five weighted sub-scores, each rated
0-100. Show every sub-score, not only the total: a 60 built from balanced
dimensions means something different from a 60 with one dimension near zero.

**The score measures fit with the job as written. It is not a probability of
getting an interview.** Referrals, timing, internal candidates, and ATS
filters are invisible to it. Use it to choose targets and to find what to fix;
use `/calibrate` to learn whether it predicts anything for this user.

Weights come from the table in `profile/rubric.md` (defaults below). Dimension
definitions are generic here and made specific by `profile/rubric.md` and
`profile/profile.md`:

| # | Dimension | Default weight | What it measures | Personalized by |
|---|-----------|----------------|------------------|-----------------|
| D1 | Domain match | 30 | Overlap between the role's core substance and the user's hands-on domains. Core-tier domains score high, adjacent-tier middle, outside low. | Domain tiers in `rubric.md` |
| D2 | Requirement coverage | 25 | List every stated must-have, mark met (1) / partial (0.5) / unmet (0), convert to a percentage. | Evidence in `cv/master.md` |
| D3 | Seniority and scope | 20 | Match between the role's level and scope (team, budget, IC vs. manager) and the user's level band. Penalize both under-leveling and reach beyond demonstrated scope. | Level band in `rubric.md` |
| D4 | Narrative fit | 15 | Does the user's throughline map cleanly onto this role's central problem? High when it does without a stretch. | Throughline in `profile.md` |
| D5 | Gap severity (inverted) | 10 | 100 minus penalties for gaps. Hard gaps are expensive; addressable gaps are cheap. | Hard-gap list in `rubric.md` |

**Total = Σ (weight × sub-score) / 100**, rounded to the nearest integer.

**Anchor.** `profile/rubric.md` names one anchor role and its score. New
scores should feel consistent with it: a role that clearly fits better than
the anchor scores higher. While the anchor is pending, the first `/score`
run finishes with setup step 6 to set it.

### Scoring discipline

- Score against the JD as written, not a charitable interpretation.
- When a requirement is ambiguous, mark it *partial* and say why.
- Note suspected external factors (referral, internal candidate, timing, ATS
  risk) in the analysis; never let them move the score.
- **Two kinds of gap, scored differently:**
  - *Hard, binary, unaddressable:* a required clearance or license not held,
    work authorization mismatch, a required degree field entirely absent, a
    regulated domain never touched, plus anything on the user's hard-gap
    list. Score these as real, weighty gaps.
  - *Addressable:* skill currency or experience that is adjacent,
    justifiable, or demonstrable (for example, directed a team doing the work
    but not recently hands-on). Flag these as *address proactively* (a
    portfolio example, a ready interview answer, naming the adjacent depth).
    They should not suppress the score or discourage applying.
- **Fit type.** Classify each role `core` or `pivot`. `pivot` when D1 or D4
  falls below the pivot threshold in `rubric.md` (default 60), or when the
  role's primary function or industry sits outside the user's throughline even
  with decent scores. For `pivot`, set a reusable `pivot_track` slug; reuse an
  existing slug from other analyses before inventing one.

## Commands

| Command | Does | Skill |
|---------|------|-------|
| `/cv-master` | Step 0: build or revise the master CV (user-drafted) | `.claude/skills/cv-master` |
| `/setup [step]` | Steps 1-6: one grill-me interview per personal setup piece | `.claude/skills/setup` |
| `/score <url, slug, or pasted JD>` | Retrieve JD, score, run the screen check, stop on a decision | `.claude/skills/score` |
| `/ats-check <slug>` | Rerun the screen check (for example after editing a CV) | `.claude/skills/ats-check` |
| `/tailor <slug> [pivot]` | Tailor the CV from the screen check's work items | `.claude/skills/tailor` |
| `/cover-letter <slug>` | Draft a cover letter in the user's voice | `.claude/skills/cover-letter` |
| `/release <slug>` | Freeze what was submitted into a case file | `.claude/skills/release` |
| `/log <slug> <outcome>` | Record an outcome | `.claude/skills/log` |
| `/calibrate` | Compare predictions with outcomes | `.claude/skills/calibrate` |
| `/dashboard` | Rebuild the pipeline dashboard | `.claude/skills/dashboard` |

Outcome ladder (ordered):
`no_response → rejected → recruiter_screen → hm_interview → onsite → offer`.
Off-ladder: `withdrawn`, `stalled`, `not_applied` (scored, never submitted;
excluded from calibration and application totals).
